One page per component: a minimal usage example and how to read the value back out. This assumes the install & setup steps are already done — the package reference, namespace imports, plus the fa-styles.css/theme.js/sidebar.js tags in your host page.

Every component is authored as plain C# (a ComponentBase/InputBase<TValue> subclass), but you consume it the normal Blazor way — tags, attributes, @bind-*, all of it.

Inside an EditForm

FaInput, FaSelect, FaTextarea, FaCheckbox, FaDate, FaCurrency are all InputBase<TValue>-derived — same as Blazor's own InputText/InputNumber, they only work inside an <EditForm>/EditContext.

Anywhere

FaToggle, FaRadioGroup, FaSearchSelect, FaDropdown, FaDateRange use a plain Value/ValueChanged pair, so @bind-Value works with or without an EditForm around it.

Install & setup

Published to GitHub Packages (not NuGet.org, for now) under parrescence. Five steps: add the feed, reference the package, import the namespaces, wire the static assets into your host page, then optionally pick a color palette — plus one more, optional, if you're using FaToastHost.

1. Add the GitHub Packages feed as a NuGet source

Pick whichever matches where you're installing from — local dev (one-time, per machine) or CI (a GitHub Actions workflow in the same account/org, no PAT needed).

Local dev

dotnet nuget add source https://nuget.pkg.github.com/parrescence/index.json \
  --name github-parrescence \
  --username <your-github-username> \
  --password <a GitHub PAT with read:packages>

⚠️ Run this yourself in a plain terminal — never through an AI coding assistant's terminal/tool-use. The token passes through that tool's context and, depending on the tool, may end up logged, transcripted, or sent to a model provider.

On Windows, leave --store-password-in-clear-text off — dotnet nuget encrypts the password at rest by default (Windows DPAPI-backed credential store). Only add that flag back on Linux/macOS if you don't have a credential provider configured (there's no OS credential store to fall back on there); if you do, treat NuGet.Config as sensitive — don't commit it, restrict its file permissions.

CI (same GitHub account/org as this repo)

permissions:
  packages: read
<!-- nuget.config -->
<configuration>
  <packageSources>
    <add key="github-parrescence" value="https://nuget.pkg.github.com/parrescence/index.json" />
  </packageSources>
</configuration>

The workflow's own GITHUB_TOKEN is sufficient — no PAT needed. GitHub Packages' NuGet feeds require authentication to read even for a public repo like this one, but a same-account workflow's own token satisfies that once granted the permission above.

2. Reference the package

dotnet add package FaFa

3. Import the namespaces

Add to _Imports.razor:

@using FaFa.Components
@using FaFa.Icons
@using FaFa.Layout

4. Wire the static assets into your host page

Razor Class Libraries ship their static assets under _content/{PackageId}/..., but they are not auto-injected into your host page — this is standard Blazor RCL behavior, not something specific to this package. Add these tags yourself:

<link rel="stylesheet" href="_content/FaFa/css/fa-styles.css" />
...
<script src="_content/FaFa/js/theme.js"></script>
<script src="_content/FaFa/js/sidebar.js"></script>

theme.js/sidebar.js are plain vanilla-JS IIFEs (no Blazor JS interop, no external dependencies) backing the theme switcher and the sidebar's collapse toggle — both persist to localStorage and stamp classes on <html>, so no Blazor component state needs to stay in sync with them.

fa-styles.css pulls one Google Font over @import (Baloo 2) from fonts.googleapis.com — a public CDN URL that works from any host, but if your app needs a strict CSP or to run fully offline/air-gapped, self-host that font instead.

5. Pick a color palette (optional)

Twenty-eight seasonal/regional/country color palettes ship in the one fa-styles.css, picked via a data-fa-palette attribute on <html> — a second, independent axis from the light/dark/colorblind mode (data-theme); any palette combines with any mode. Default is northwest-fall (no attribute needed) if you skip this step.

Available names: northwest-fall, southwest-summer, northeast-spring, midwest-winter, southeast-beach, greece-aegean, spain-flamenco, ireland-emerald, jamaica-blue-mountain, japan-indigo, korea-celadon, china-cinnabar, india-peacock, cameroon-rainforest, sahara-desert, brazil-rainforest, brazil-favela, portugal-tiles, spain-bullfighting, mexico-day-of-the-dead, london-life, new-york-nightlife, india-henna, ruckus, dinner, hang-in, floating, fit.

Option A — pick one at build time

<html lang="en" data-fa-palette="southeast-beach">

Option B — switch palettes at runtime

Drop in the bundled dropdown:

<FaPaletteSwitcher />

See FaPaletteSwitcher for details. Or call the underlying function yourself, the same way <FaThemeSwitcher> calls window.faSetTheme(...) — built-ins only:

window.faSetPalette('southeast-beach');
// or window.faSetPalette('northwest-fall') / window.faSetPalette(null) to reset

Option C — bring your own palette at runtime

In addition to the twenty-eight built-ins, pass FaPalette objects to FaPaletteSwitcher's CustomPalettes parameter:

<FaPaletteSwitcher CustomPalettes="_myPalettes" />

@code {
    private readonly FaPalette[] _myPalettes =
    [
        new FaPalette(
            Value: "acme-brand",
            Label: "Acme Brand",
            Colors: new FaPaletteColors(
                Primary: "#2454ff", PrimaryDark: "#1638b0", PrimaryLight: "#7a9bff",
                Footer: "#eef1fb", Glow: "#3f6bff", Gold: "#d9a441", Accent: "#00a389",
                AccentDark: "#00786a", Ember: "#c0392b", Wine: "#6b1f2a", Fir: "#20242b",
                Cream: "#f7f8fc", Surface: "#ffffff", Text: "#1b1f2a", TextMuted: "#5c6270",
                TextOnPrimary: "#ffffff", Border: "#c9d2ec", BorderFocus: "#1638b0",
                AlertDangerBg: "#fbeaea", AlertSuccessBg: "#e3f5f1", AlertInfoBg: "#eaf0fc"),
            DarkOverrides: new FaPaletteDarkOverrides(
                Cream: "#14161d", Surface: "#1c1f29", Text: "#eef0f7", TextMuted: "#a3a9ba")),
    ];
}

A custom palette has no compiled CSS of its own — its colors travel as JSON on the <option> itself and get applied as inline --fa-* custom properties on <html> at selection time. Only Colors is required; DarkOverrides is optional and only needs the tokens that should actually change in dark mode.

Options A–C persist the choice to localStorage under fa-palette (a custom palette's colors also go into fa-custom-palette) and stamp data-fa-palette on <html> (skipped for a custom palette).

Option D — override colors directly with your own CSS

No picker at all. Every component reads color exclusively through the --fa-* custom properties :root defines — so redeclaring any of them in your own stylesheet, loaded after fa-styles.css, silently wins over whichever built-in palette is active, no FaPalette/C# involved:

/* your-app.css, linked after fa-styles.css */
:root {
  --fa-primary: #2454ff;
  --fa-primary-dark: #1638b0;
  --fa-accent: #00a389;
  /* ...override only the tokens you actually want to change; every token this
     omits keeps coming from whichever built-in palette is active. */
}

Combines fine with A–C too — your override CSS wins over whichever built-in/custom palette happens to be active for any token it redeclares, since it loads later in the cascade. Handy for "start from a built-in palette but tweak two or three tokens" without hand-copying the other eighteen.

Whichever of A–C you use

Add this inline snippet to your host page's <head>, before the fa-styles.css <link> from step 4, so a returning visitor's saved mode/palette applies before first paint instead of flashing the default and then jumping:

<script>
  (function () {
    var theme = localStorage.getItem('fa-theme');
    if (theme) document.documentElement.setAttribute('data-theme', theme);
    var palette = localStorage.getItem('fa-palette');
    // A "custom:..." palette has no compiled CSS to select via the attribute — its
    // colors get applied as inline custom properties by theme.js once it loads, so
    // there's a brief flash of the default palette for that case only; skip the
    // attribute here rather than stamping a value nothing selects on.
    if (palette && palette.indexOf('custom:') !== 0) {
      document.documentElement.setAttribute('data-fa-palette', palette);
    }
  })();
</script>

6. Customize typography & shape (optional)

--fa-font is a single global custom property (same architecture as the color tokens above) — every component reads its font through it, so swapping it in your own stylesheet, loaded after fa-styles.css, reskins the whole library's typography with no FaFa code involved:

/* your-app.css, linked after fa-styles.css */
:root {
  --fa-font: 'Inter', system-ui, sans-serif;
}

A handful of other palette-agnostic "standard" tokens work the same way — defined once in :root, reused everywhere, and safe to override the same way:

TokenDefaultControls
--fa-radius-sm / -md / -lg / -pill8px / 14px / 22px / 999pxCorner rounding — small controls, cards/panels, large surfaces, pill shapes
--fa-border-width2pxStandard border weight everywhere a component draws one
--fa-transition-fast / -medium0.15s ease / 0.2s easeHover/focus color & shadow changes vs. size/layout changes

Not overridable this way: per-component padding/margin/gap and most font-size/font-weight values — those are deliberately hand-tuned per component rather than drawn from a shared scale. Target that component's own class in your own CSS instead of looking for a token.

7. Set a favicon / app icon (optional)

This library ships no favicon of its own — like BrandText, it's your app's own branding, not something a style library should hardcode. Add the usual <link> tags to your host page's <head> yourself, the same as any Blazor app:

<link rel="icon" type="image/png" href="favicon.png" />
<link rel="apple-touch-icon" href="apple-touch-icon.png" />

Want a logo next to your app's name in the header/sidebar chrome itself (distinct from the browser-tab favicon above)? That's BrandIconUrl on FaHeader / the page shells / templates.

8. Using FaToastHost (optional)

Every other component here needs zero C#-side setup — import the namespace and use the tag. FaToastHost/FaToastService is the one exception: register the service once before mounting <FaToastHost />.

// Program.cs
builder.Services.AddScoped<FaToastService>();

FaModal

Backdrop-covered dialog. You own the open/closed state — FaModal renders nothing when Show is false, so you can gate closing behind your own logic before flipping it.

Usage

<FaButton OnClick="() => _showDeleteModal = true">Delete item</FaButton>

<FaModal Show="_showDeleteModal" Title="Confirm delete" OnClose="() => _showDeleteModal = false">
    <p>Are you sure you want to delete this item? This can't be undone.</p>

    <FooterContent>
        <FaButton Variant="FaButtonVariant.Secondary" OnClick="() => _showDeleteModal = false">
            Cancel
        </FaButton>
        <FaButton Variant="FaButtonVariant.Danger" OnClick="ConfirmDeleteAsync">
            Delete
        </FaButton>
    </FooterContent>
</FaModal>

@code {
    private bool _showDeleteModal;

    private async Task ConfirmDeleteAsync(MouseEventArgs e)
    {
        await _itemService.DeleteAsync(_itemId);
        _showDeleteModal = false;
    }
}

Getting the value: no bound value. OnClose fires on backdrop click or the header's close button — you decide whether to actually flip Show back to false.

Position, size, and closing

<FaModal Show="_show" Title="Filters" OnClose="() => _show = false"
         Position="FaModalPosition.Right" Size="FaModalSize.Small"
         ShowCloseButton="false" CloseOnBackdropClick="false">
    ...
    <FooterContent>
        <FaButton OnClick="() => _show = false">Close</FaButton>
    </FooterContent>
</FaModal>

ShowCloseButton="false" + CloseOnBackdropClick="false" together means the only way out is an explicit action in FooterContent. FooterAlign controls the footer button row's justify-content — Between puts a destructive action on the left and Cancel/Confirm on the right without a manual spacer.

Page templates

Page templates

Four full-page compositions in namespace FaFa.Templates (@@using FaFa.Templates), each built on FaStandardShell/FaSidebarShell plus whatever one recurring page shape needs beyond the bare shell: FaDashboardTemplate (sidebar shell + title/actions row), FaFormTemplate (standard shell + centered card), FaHomeTemplate (standard shell + hero band), FaAuthTemplate (chrome-free centered card).

They're routed pages, not layouts — use one directly on a @@page-attributed .razor file, rather than wrapping @@Body in your MainLayout.razor. Every shell-level parameter (BrandText, auth props, Sidebar, FooterContent, each bar's own FaNavPosition) uses the exact same name as the shell it wraps — see layout shells for what each one does.

Usage

@@page "/dashboard"
@@using FaFa.Templates

<FaDashboardTemplate BrandText="MyApp" BrandHref="/" Title="Overview">
    <Sidebar><NavMenu /></Sidebar>
    <Actions><FaButton Variant="FaButtonVariant.Primary">New report</FaButton></Actions>
    <ChildContent><FaCard>Dashboard body here.</FaCard></ChildContent>
</FaDashboardTemplate>

Getting the value: pure layout, no bound value of its own — see each template's own section below for its parameters.

FaHeader, FaFooter, FaSidebar are the individual pieces; FaStandardShell and FaSidebarShell compose them into the two full-page templates. Most consumers only touch the two shells, from MainLayout.razor.

FaStandardShell — header + content + footer, no sidebar

<FaStandardShell BrandText="MyApp"

    @Body

FaHeader/FaFooter/FaSidebar each also take their own Position="FaNavPosition.___" when used directly (not through a shell) — Standard scrolls away with the page, Sticky pins to that bar's edge of the viewport, Floating is the same pinning inset with margin/rounded corners. Pinning the sidebar additionally switches it to its own internal scroll (overflow-y: auto) and settles it in right below the header (offset by --fa-header-height, a fixed 4rem also enforced as FaHeader's own min-height) instead of underneath it, since it no longer scrolls away with the rest of the page once stuck full-height.

By default a shell's .fa-shell only sets min-height: 100vh, so the whole page grows past one viewport and scrolls as a single document — right for most pages, wrong for a dashboard-style page that wants the header/sidebar/footer pinned to the viewport edges with only <main> scrolling internally. Set ContainScroll="true" on either shell for that instead (a separate opt-in .fa-shell-contained class, so existing whole-page-scroll consumers are unaffected). A Standard-position sidebar taller than the viewport scrolls independently under ContainScroll too, same as Sticky/Floating already do.

FaSidebar's own Collapsible (default false) controls whether its icon-only collapse toggle renders at all — that's a desktop-only affordance, separate from small-screen behavior below. Turn it on only once every link in the sidebar has its own FaIcon + .fa-sidebar-link-text wrapper; a link with no icon has nothing to show at 64px wide, so it's hidden while collapsed rather than left to wrap.

Below 720px wide, FaSidebar goes off-canvas — hidden until opened — regardless of Collapsible. FaSidebarShell automatically shows a hamburger button left of the brand at that width (FaHeader.ShowSidebarToggle, set for you) that reveals the sidebar as a full-width row below the header; tapping it again hides it. This is also independent of Position — Sticky/Floating's pinned-full-height styling is reset at this breakpoint too, so every Position collapses into the same off-canvas row. Using FaHeader/FaSidebar directly, set ShowSidebarToggle="true" on FaHeader yourself for the same behavior.

FaPaletteSwitcher

A single dropdown covering all twenty-eight color palettes, plus any consumer-supplied ones passed via CustomPalettes. Mostly no Blazor state: picking a built-in option calls window.faSetPalette(...) from theme.js directly, client-side only — every <FaPaletteSwitcher> on the page stays in sync with whichever palette is actually active, including the one restored from localStorage on first paint. A separate, independent axis from FaThemeSwitcher's light/dark/colorblind mode — any palette combines with any mode.

Usage

<FaPaletteSwitcher />

Adding your own palettes

The twenty-eight built-ins are precompiled into fa-styles.css and selected purely by name. A palette you define yourself has no compiled CSS to select, so it's expressed instead as an FaPalette object (FaFa.Components) and passed via CustomPalettes — see Install & setup, Option C for a full example. Each renders as its own <option value="custom:{Value}"> carrying its Colors/DarkOverrides as JSON data attributes; picking it applies those colors as inline --fa-* custom properties on <html> instead of stamping data-fa-palette.

Caveat: because a custom palette's colors live in the rendered <option>, not compiled CSS, the pre-paint "avoid a flash of the wrong palette" snippet (Install & setup) can't apply one before Blazor mounts — expect a brief flash of the default/previous built-in palette on reload for a custom selection.

Don't want a picker at all — just reskinning the app to one fixed brand? Skip this component and override the --fa-* custom properties directly in your own CSS instead (Install & setup, Option D); both approaches read the same tokens, so a plain-CSS override still wins over whatever this component last selected.

Getting the value: nothing to bind — current palette lives in localStorage (fa-palette key, plus fa-custom-palette for a custom selection's colors) and the data-fa-palette attribute on <html> (absent for the northwest-fall default and for any custom palette, which uses inline --fa-* properties instead), both managed by theme.js. Read localStorage.getItem('fa-palette') yourself if your own code needs it.

FaInputStyleSwitcher

Three buttons — Standard / Minimal / Maximal — for the global input-style axis: a third, independent axis alongside palette and theme mode, all stamped as data attributes on <html>. Unlike FaInput/etc.'s own per-instance Size, this retunes every boxed native-input-like control (FaInput, FaSelect, FaTextarea, FaCurrency) app-wide. No parameters, no Blazor state — picking a button calls window.faSetInputStyle(...) from theme.js directly, client-side only.

Usage

<FaInputStyleSwitcher />

The three styles

Standard (default, no attribute needed) — today's look. Minimal — 1px border, square corners, no shadow. Maximal — 3px border, larger radius. Only FaInput/FaSelect/FaTextarea/FaCurrency participate — the flattened controls (FaCheckbox, FaToggle, FaDate, ...) were never boxed the same way to begin with.

Getting the value: nothing to bind — current input style lives in localStorage (fa-input-style key) and the data-fa-input-style attribute on <html> (absent for the standard default), both managed by theme.js.

Layout & chrome

FaUiStyleSwitcher

Three buttons — Flow / Terse / Typewriter — for the global UI-style axis: a fourth, independent axis alongside palette, theme mode, and input style, all stamped as data attributes on <html>. Unlike input style, which only retunes boxed inputs, this retunes the shared shape/type/motion tokens (radius, font, border-glow shadow, transition speed) nearly every component draws from. No parameters, no Blazor state — picking a button calls window.faSetUiStyle(...) from theme.js directly, client-side only.

Usage

<FaUiStyleSwitcher />

The three styles

Flow (default, no attribute needed) — today's look: rounded font, 8/14/22px radii, a colored border-glow shadow, animated transitions. Terse — a flatter, editorial look: plain system font, 4/6/10px radii, no shadow, no transitions. Typewriter — a clean, minimal paper-like look: real monospaced serif font (Courier New), moderate 6/10/16px radii, a thinner 1px border, and one soft, low-opacity neutral "resting" drop shadow instead of the colored glow — focusing something nudges the shadow up slightly rather than tightening it; motion stays at Flow's normal speed. Status pills (badges/chips) keep their pill radius in all three, picking up an uppercase, tracked-out, monospace label under Terse.

Getting the value: nothing to bind — current UI style lives in localStorage (fa-ui-style key) and the data-fa-ui-style attribute on <html> (absent for the flow default), both managed by theme.js.
